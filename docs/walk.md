# Town Walk (proof of concept): a pixel town where the server counts what you collected

A top-down town map. The student's wolf walks around, picks up six items (each a short money fact) and walks through building doors that open the existing building screens. Same trust model as the Arcade (`docs/arcade.md`): the browser walks a fixed-step, integer-only core and records its inputs; the server replays those inputs through the **same file** with a seed it chose, and the count is whatever the replay says.

## As built

**Files.** `modules/walk/index.js` (routes, table, throttle), `modules/walk/ui/town/town-core.js` (map and game, shared by server and browser, no imports), `ui/town/town.js` (camera, input, tap to move, 30 ticks/s loop), `ui/town/art.js` (every tile, building, sprite and item drawn from rects and small pixel maps, no image or font files), `ui/town/pixfont.js` (3x5 font, copied from the arcade so walk works without it), `ui/town/facts.js` (door names and the fact text per item), `ui/walk.js` + `walk.css` (the building). Enabled in both courses right after `arcade`, before `savings` (pinned in `test/db.test.js`). Panel: key `walk`, title "Town Walk".

**Flow.**
1. `POST /api/walk/start {}`: season must be active (409), at most 12 starts an hour per student (429, in memory, `options.walk.startsPerHour`). Writes a `walk_runs` row (random 128-bit hex id, server-chosen 32-bit seed, `open`); an older open visit of that student becomes `superseded`. Returns `{ session, seed, max_ticks: 5400, items: [{ id, kind, x, y }] }`. The items are `placeItems(seed)`, sent so the client need not re-derive them; the server never trusts anything the client sends back about them.
2. The browser walks and records `[[tick, mask], ...]`, one entry whenever the held mask changes. Mask bits: 1 up, 2 down, 4 left, 8 right.
3. `POST /api/walk/finish { session, ticks, inputs }`. `ticks` is a whole number 1..5400, `inputs` at most 2000 `[tick, mask]` whole-number pairs with strictly increasing ticks in 0..ticks-1 and masks 0-15 (a malformed body is a 400 and does not burn the visit). Any `collected`, `score` or `items` field in the body is ignored. The visit must be this student's (404), `open` (409 otherwise) and under 15 minutes old (else it becomes `expired`, 409). The replay runs outside any transaction, then one transaction does `UPDATE ... WHERE status = 'open'` and checks `changes` (a double finish is a 409). Response: `{ collected, items: [ids in the order collected], best, visits, new_best, ticks }`.
4. Wall-time guard: if less than 40% of `ticks / 30` seconds has passed since `start`, the run is stored `rejected` with `flag = 'fast'` and the finish is a 422. It is a lazy-bot-batch guard, never an input to the count.
5. When the replay found 3 or more items, **after** the transaction commits and only when the UPDATE changed a row, the module emits `module.walk.collected { playerId, worldId, collected }`.
6. `GET /api/walk/state` (no writes): `{ world_active, my_best (most items in one visit this world), visits, items: 6, max_ticks }`. No leaderboard.

**Table** `walk_runs` (`mod:walk:001_runs`): `id, player_id, world_id, seed, ticks, collected, status (open | finished | rejected | expired | superseded), flag, started_at, finished_at`. Inputs are not stored.

**Errand.** `modules/today/errands.json` gets one entry, `walk-stroll` "Take a stroll through town and collect 3 items": module `walk`, building `walk`, priority 5, 50 cents x price index, energy 1, done by `module.walk.collected`. Completion is idempotent and only happens when it is among that day's three picks. Nothing else in `today` changed. No stress, wage, ledger or promotion effect: money only moves through the existing errand reward path.

**Core constants** (`C` in `town-core.js`): 30 ticks/s, 5400 ticks (3 minutes), 8 px tiles, map 64 x 48 tiles = 512 x 384 px, player box 4 x 4 px (feet), speed 1 px per tick (30 px/s, 3.75 tiles/s), a diagonal moves 3 ticks in 4, blocked-move nudge up to 3 px (so doors and corners are not pixel-exact targets), pickup radius 6 px from the box centre to the item centre, 6 items per visit at least 6 tiles apart (largest of |dx|, |dy|) and at least 6 tiles from the spawn, 2000 inputs max. The core has no imports, no `Math.random`, no `Date`, no floats and no division (a test scans the source). A full 5400-tick replay with 1800 input changes takes about a millisecond (a test asserts < 20 ms, cold).

**Items.** `placeItems(seed)` seeds mulberry32 + FNV-1a (same as the arcade), shuffles the 8 kinds (receipt, paystub, statement, t4, coupon, bill, keycard, coin-purse) and takes 6, then draws candidate tiles: walkable, not a door, reachable from the spawn, spaced. The fact text per kind (Alberta / Canada, 1-2 plain sentences) lives in `ui/town/facts.js`.

**Map layout** (the strings in `MAP`, read them as a picture). Border of trees. A plaza (13 x 13, fountain in the middle) with the spawn south of the fountain; Job Centre and Bank of DAA on its north side; Bank and Arcade either side of the main east-west avenue just above it. A top street with six everyday-money buildings (housing, insurance, credit on the west; bills, outfitters, exchange on the east) and a bottom street with five long-run ones (net worth, venture row, amphitheatre on the west; life, retirement on the east). A park with a pond south of the plaza, a north-south avenue, scattered trees. Fifteen doors, one per building key: job, bank, bank-of-daa, housing, insurance, credit, bills, outfitters, exchange, networth, venture-row, amphitheatre, life, retirement, arcade. Each building is a solid 5 x 4 tile block with one walkable door tile in the middle of its south face. `walk` itself is not a door. Short signs (JOBS, BANK, RATES, HOMES, INSURE, CREDIT, BILLS, SHOP, MARKET, NET WORTH, VENTURES, SCORES, LIFE, RETIRE, ARCADE) are drawn with the pixel font.

**Client.** 160 x 120 logical canvas scaled by whole numbers (x1-x4, `walk-x*` classes), camera follows the wolf and is clamped to the map. Controls: arrows or WASD; an on-screen d-pad (4 buttons, 64 x 56 px, pointer events, press and hold); tap or click the map to walk there. Tap to move runs a breadth-first search over the same tile grid (`distField` and `autoMask`, both in the core) and emits the same 4-bit masks every tick, so what is recorded is what is replayed; any key or d-pad press cancels it, and tapping a building walks to its door. Door entry: standing on the door tile of a building in `me.panels` shows "ENTER BANK" for 12 ticks (0.4 s), then the visit is finished (POST `finish`, waited for up to 2.5 s) and `location.hash` becomes `#<key>`. A door whose panel is not in `me.panels` is drawn shut and shows "CLOSED". The visit also auto-finishes on Leave, when the 3 minutes end, when the tab is hidden, and when the panel is torn down mid-visit. Errand markers: the building fetches `/api/today/state` (read only) and draws a bobbing "!" over the door of each open errand's building. After a visit: the server's count, the facts for what was collected, and whether the errand is done. A network failure on finish keeps the inputs and offers "Try sending again". The loop does at most 4 catch-up ticks a frame and drops the rest, so a slow device runs slower than real time rather than skipping.

**Relation to the arcade.** Same files-shared-by-server-and-browser design, same start/finish/replay/guard shape, same copied hash and RNG, different game. It is a separate module with its own table; it does not import anything from `arcade` (the pixel font is copied). The ARCADE door just navigates to `#arcade`.

## Teacher panel ("Town Walk"), live roster and the presence switch

`GET /api/walk/teach` and `POST /api/walk/settings` are teachers only (students 403) and cover the classes the teacher reads (`k.players.classesFor` / policy `class.manage`: another teacher's class is a 404 and never appears in the list). `modules/walk/ui/teach.js` draws it.
- **Counts (this season).** Per class: `visits` (finished), `rejected` plus `rejected_by` (flag, today `fast`), `players` (distinct students with a verified visit) and `items`, the finished visits bucketed by items collected: `0-2`, `3-5`, `6`.
- **On the map now.** `on_map: { count, players }` is read from the in-memory presence table (entries older than 10 s are skipped), pseudonyms only. It stays live without polling: the server pushes `walk.roster { class_id, count, players }` (skippable, at most 100 names) to the class's teachers, found in `class_teachers`, only when someone joins or leaves the map or an entry expires, never on a move; the panel updates the line from it. A page that was closed simply reads the roster again when it opens.
- **Presence switch.** Migration `002_class_settings` adds `walk_class_settings (class_id PRIMARY KEY, presence 0/1, changed_at)`. A row overrides `options.walk.presence` for that class; no row means the config default. `POST /api/walk/settings { class_id, presence }` (`k.input.int` and `k.input.bool`, 400 on anything else) upserts it and writes `walk.presence` to the audit log (`{ class, presence }`, actor `player:<teacher>`). Turning it off, at once: the class's entries are dropped from memory, its teachers get an empty roster, its connected students get `walk.presence.off` (the map hides everyone and stops posting; `presence.js` handles it), and `/pos` and `/leave` answer `{ presence: false }` for that class from then on (other classes are untouched). `/api/walk/state` carries the effective `presence` for the student's class. Turning it on needs nothing pushed: a student who already has the map open keeps it as it is until they reopen Town Walk.
- **Ceilings.** The switch is per class, not per student; the emote buttons stay on screen (inert) for a student whose class was switched off while they were playing; one extra `walk_class_settings` read per `/pos` (an indexed primary-key lookup).
- **Tests.** `test/arcade-walk-teach.test.js` (scoping, counts, the switch, persistence and the migration run twice, the roster event). `test/presence.test.js` still asserts no position is stored; its "no schema mentions presence" check now skips this one settings table.

## Not verified / known ceilings

- A determined player can compute a perfect-path input log offline (the seed and item positions are returned at `start`) and submit it. Rewards are capped (one 50-cent errand a day), so the stakes are low. Hiding the seed is not possible with this design.
- Tap-to-move pathing is client-side. The server only sees the resulting masks.
- Presence is cosmetic and spoofable; see "As built (presence)" below for what it does and does not promise.
- Errand markers read today's state once at the start of a visit; they do not update during it.
- The errand shows wherever the `walk` module is loaded (today filters templates by `k.modules.has`, not per course); with both courses enabling it that is exact.
- Not tested on a real phone. Browser-checked at 375 px (x2, 324 px canvas, no horizontal overflow, pads 64 x 56 px) and at desktop (x4), with synthetic key and pointer events only. The in-app browser draws about one frame a second, so the checks ran with a `requestAnimationFrame` shim (a `setTimeout` at 33 ms, and for the full item run a manual frame pump that fed exactly one tick per frame). The "closed door" drawing was not seen in a browser (both courses enable every building). A real human's feel (speed, how the d-pad handles) is untested.
- A hidden tab (or the browser pane toggling visibility while a screenshot is taken) ends the visit and sends it; it can then not be continued.
- The map is one static layout. Items are random per visit, buildings are not.

## As built (presence)

Classmates on the Town Walk screen at the same moment see each other as small wolves with a pseudonym tag, and can send three canned emotes. It is cosmetic and non-authoritative: no money, no errands, no ledger, nothing in the database, and it is not part of the recorded inputs, so the replay and the item count are untouched.

**Files.** `modules/walk/index.js` (the in-memory table, `POST /pos`, `POST /leave`, the 500 ms broadcaster), `ui/town/presence.js` (sends your position, receives snapshots, interpolates and draws the others), `ui/town/art.js` (8 classmate palettes, emote icons), `ui/town/town.js` (calls `presence.frame/draw/drawSelf`, keys 1/2/3), `ui/walk.js` + `walk.css` (HUD line, three emote buttons, `pagehide`). Plus a generic kernel capability, `k.push` (`docs/modules.md`, `docs/events.md`).

**Flow.**
1. `GET /api/walk/state` now includes `presence: true|false` (the effective value for the student's class: the teacher's per-class switch if set, else the config default). The UI builds presence only when it is true.
2. While the visit screen is open the browser `POST /api/walk/pos {x, y, dir, emote?}` at most every 250 ms, only when something changed (or every 2 s as a heartbeat). `x` 0..511, `y` 0..383, `dir` 0..3 (down, up, left, right), `emote` 0..3 (0 or absent = no new emote, 1 wave, 2 thumbs-up, 3 star). Whole numbers only; any other field, a float, an out-of-range value or a non-object body is a 400. Student only, season must be active (409 otherwise), module must be enabled for the course (404). At most one accepted post per 200 ms per player: a faster one is dropped with `{ ok: true, dropped: true }` (not an error; the client sends again).
3. The server keeps `classId -> playerId -> { username, x, y, dir, emote, seen }` **in memory only**. An entry ends 10 s after its last post, on `POST /api/walk/leave {}` (the client sends it when the visit or panel ends, with `keepalive`, so a closed tab's sprite goes within about a second), when the player's session ends (`session.revoked`), or when the season closes. An emote lasts 2.5 s on the server too and then goes back to 0.
4. One `setInterval` (500 ms, `options.walk.presenceTickMs`, `unref`'d) runs only while any entry exists; it starts at the first post, stops when the table is empty and is cleared on `app.closing` (core event, emitted by `server.js` `close()`; the only lifecycle hook added). Each tick prunes, then for every class that changed since its last broadcast (or has been quiet for ~3.3 s, a keepalive) it builds one list sorted by username and, for each member who has an entry, calls `k.push([thatPlayer], 'walk.presence', { players: [{ u, x, y, d, e }, ...] }, { skippable: true })`: the others only (never yourself), at most 40, only entries seen in the last 10 s. A player who is alone and was already told so gets nothing.
5. The browser draws each classmate between the camera view and your own sprite (others first, you on top): linear interpolation toward the newest position over 500 ms, palette from a hash of the username (8 palettes, none with your blue vest), a 3x5 pixel-font tag (10 characters), an emote icon above for 2.5 s, culled when outside the view. A snapshot is the whole list: anyone missing has left; an entry also expires locally after 10 s of silence. The HUD says "N classmates here" (0 when you are alone). Emote buttons are 56 x 48 px; keys 1/2/3. Your own emote shows at once.
6. Failures are silent. After a network error, 429 or 409 the browser stops posting for 5 s. Presence never blocks the 30 ticks/s loop: `frame()` is called once per rendered frame, outside the step loop, and does at most one small POST per 250 ms.

**Privacy rules.** Pseudonyms only: the username is the school-issued AdjectiveAnimalNN pseudonym, and a snapshot holds that and five numbers, nothing else (a test asserts no ids and no class names). Same class only, same season only. Memory only (a test asserts no new table and no new row). No chat and no free text: the only things a player can send are two coordinates, a direction and a number 0-3. Teachers' streams get nothing (they are not class members with an entry, and `k.push` only reaches the listed ids).

**Config.** `options.walk.presence` (boolean, default true) in `config/vdaa.json`. `false`: `/pos` and `/leave` answer `{ presence: false }`, nothing is stored or broadcast, `/state` says `presence: false`, the UI shows no classmates and no emote buttons. This is only the default for a class: the teacher's switch in the Town Walk panel (below) overrides it per class, in either direction, without a restart.

**Cleanups in the same wave.** (a) Closing the tab mid-visit: the finish POST is now always a `fetch` with `keepalive: true` (so it survives the unload), and a `pagehide` handler ends the visit if `visibilitychange` (which fires first in a real close) has not already; every path sends exactly one finish; (b) pressing Leave before the first tick cancels the visit quietly (no finish call, no 400); (c) the window `resize` listener added by each visit is removed when the visit ends.

**Ceilings.**
- Positions are cosmetic and spoofable: a client can post any position, so a classmate can appear anywhere, face any way, or show an emote at will. Nothing depends on them.
- Teachers see only the roster (pseudonyms, in the Town Walk panel), never positions.
- In memory only: a server restart empties it (clients refill it within 2 s).
- Per-class cap of 40 listed classmates; with more, each player sees the first 40 others in username order.
- A snapshot is about 55 bytes a player, up to roughly 2.2 KB, under `k.push`'s 4 KB limit.
- Each post goes through the normal session check, which refreshes the session's idle clock, but only while a visit is running: the loop stops at 3 minutes (a slow device at most about 22 minutes), and a new visit needs a click, so an open tab cannot keep a shared computer logged in indefinitely.
- A backed-up socket skips snapshots (they are `skippable`); the next one carries the full list.
- Measured (`test/presence.test.js`, 45 students in a class, 30 posting every 250 ms for 3 s, 30 streams open): about 1.85 snapshots per second per stream, broadcast cost per tick well under 10 ms (see the test output), an unrelated request during the load took single-digit ms.
